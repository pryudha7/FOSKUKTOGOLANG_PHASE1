# Pre-Screening Check executor runs in the backend process, coordinated through the database

The Pre-Screening Check run (FR-PSAPI-001/002) is executed by goroutines inside the backend process (`internal/cases`), not by a separate worker service or a message queue. The run row (§9.15) is the only coordination point: an executor owns a run through `owner_id` and a heartbeat every 15 s, a recovery sweep at start and every 60 s takes over runs whose heartbeat is stale with the atomic UPDATE of DB-RULE-047, and the partial unique index of DB-RULE-046 keeps at most one active run per case. We chose this because the SoT already defines executor ownership, take-over and in-memory retry timers in terms of that table, so several backend instances can run side by side and a crashed one is resumed by another, without running and deploying extra infrastructure. The cost: run execution shares the backend's lifetime (`app.New` returns an `*App` whose `Close` stops the executor), and two take-over races have no deterministic test.
